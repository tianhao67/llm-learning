# 评测说明

这份文档说明项目的评测方法、指标含义和复现方式。评测的目的不是证明「模型很聪明」，
而是回答一个工程问题：**改了提示词或检索参数之后，效果是变好还是变差？**

## 评测集

所有样本放在 `evals/cases/` 下，每行一个 JSON 对象，方便 diff 和逐条追加。

| 文件 | 数量 | 用途 |
| --- | --- | --- |
| `classify.jsonl` | 38 | 情感分类，三类各 10 条，另加 8 条「无明显情感词」的隐式表达 |
| `survey.jsonl` | 12 | 问卷建议，每条给出 `must_include` 关键词，代表回答应覆盖的要点 |
| `rag.jsonl` | 15 | 课程笔记问答，标注正确答案所在的文档 id 和关键术语 |

样本都是自己写的，规模不大，结论只对本项目有效，不要当成模型能力的普适结论。

## 三种任务

### 1. 情感分类（`classify`）

- 提示词：`PROMPT_PATTERNS["classify"]`，要求只输出一个词；
- 指标：准确率、宏平均 F1（三类均衡，但 F1 仍比准确率更能反映单类表现）；
- 归一化：模型可能输出 `正面`、`positive` 或带标点，`normalize_label` 统一映射；
- 无法识别的输出计为错误，并单独统计 `invalid` 数量。

### 2. 问卷建议（`survey`）

对比三个提示词版本：

| 版本 | 内容 | 想验证的假设 |
| --- | --- | --- |
| `v1` | 只有指令 | 基线 |
| `v2` | 指令 + 两组少样本 | 示例能否提升要点覆盖 |
| `v3` | 指令 + 示例 + 约束 | 约束能否让输出更短、更结构化 |

- 指标：关键词覆盖率（`must_include` 命中比例）、分点格式率（是否用列表作答）、
  平均字数、通过率（覆盖率 ≥ 0.6 且长度在 80~900 字之间）；
- 关键词覆盖是粗粒度代理指标，不代表建议质量。正式使用时建议再加人工评分
  （每条 1~5 分），本文档的结论需要结合人工抽查理解。

### 3. RAG（`rag`）

先只看检索，再加 `--generate` 看生成。

- `recall@k`：前 k 个 chunk 中包含标注文档的样本比例。它衡量「资料找没找到」，
  是检索环节最直接的指标；
- 关键词覆盖率：答案是否包含标注的关键术语；
- 引用合法率：回答中的 `[n]` 是否都落在实际检索结果范围内（`n ≤ len(hits)`）。

生成部分还会检查模型是否「编引用」：如果回答里出现 `[9]` 但只检索了 3 条资料，
`invalid_citations` 就不为空，界面和报告都会提示。

## 复现方式

```bash
pip install -e ".[dev]"

# 先小样本试跑，确认配置和费用
python evals/run_eval.py --task classify --limit 5

# 完整评测
python evals/run_eval.py --task classify
python evals/run_eval.py --task survey --variants v1,v2,v3
python evals/run_eval.py --task rag --top-k 3 --generate
```

结果会打印到终端，并写入 `evals/results/<task>.md`，可以直接贴进 README。
脚本对每次调用都固定 `temperature=0`，同一份提示词多次运行的结果应当接近；
如果波动明显，说明任务本身不稳定，需要增加样本量。

## 成本估算

以 DeepSeek 为例，一次完整评测大约 70 次调用：

- 分类：38 次短请求（每次输出不到 10 token）；
- 问卷：12 条 × 3 个版本 = 36 次，输出约 300~700 token；
- RAG：15 次检索（不花钱）+ 15 次生成。

总花费在几分钱量级，具体取决于模型单价。先跑 `--limit 5` 是个好习惯。

## 局限

- 样本量小，指标波动大，不能用于模型选型的强结论；
- 关键词覆盖无法判断建议是否「正确、可行」，只能说明有没有提到关键点；
- RAG 检索使用 TF-IDF，没有语义泛化能力，换成 embedding 后指标会变化；
- 评测没有覆盖多轮对话、长文档、并发等场景。

## 怎么加样本

1. 往对应 `jsonl` 追加一行，字段参照现有样本；
2. 分类样本确保标签清晰，避免模棱两可的句子；
3. 问卷样本的 `must_include` 写 3 个左右「好建议大概率会提到」的词；
4. RAG 样本的 `expected_doc` 用文件名去掉 `.md`，`expected_terms` 写原文中出现过的词；
5. 重跑评测，把 `evals/results/*.md` 一起提交，方便对比历史。
